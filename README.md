# KiniQ — 만성신장질환 조기 발굴 및 생활습관 중재 서비스

40세 이상 만성신장질환(CKD) 위험군이 건강검진 결과를 입력하면 위험 단계(G1~G4)를 배정받고,
그 단계에 맞는 생활습관 챌린지와 대시보드를 제공받는 헬스케어 웹 서비스입니다.

이 저장소는 팀 프로젝트 원본 [AI-HealthCare-03/AH_03_02](https://github.com/AI-HealthCare-03/AH_03_02)의
개인 포크이며, 이 README에는 **제가 맡은 부분**을 정리했습니다.

## 담당한 일

**사용자 화면 전 구간**
검진 결과 입력 → 위험군 배정 → 챌린지 → 대시보드. 대시보드는 8개 커밋 단위로 나눠 작업했고
26주 잔디 히트맵, 라디알 미니차트, 사구체여과율(eGFR) 시뮬레이션, 감정 듀얼축 그래프를 포함합니다.

**백엔드**
services · apis · repositories · dtos · models · core · tests 계층을 기능 단위로 함께 작업했습니다.

**검진 결과지 OCR 자동 입력** — [`app/services/ocr.py`](app/services/ocr.py)
검진 결과지 사진이나 PDF를 올리면 NAVER CLOVA OCR로 글자를 읽어 혈압·공복혈당·콜레스테롤·중성지방·
크레아티닌·키·체중·허리둘레 등 10종을 입력 칸에 자동으로 채웁니다. 여러 쪽짜리 PDF는 쪽 단위로 나눠 처리합니다.

**캐릭터 일러스트 시스템**
Gemini로 생성한 PNG 10~13장에 SVG·이모지 폴백을 붙이고, 진화 단계를 4단계에서 3단계로 줄였습니다.

**보안 필수 항목 8건**
로그인 요청 횟수 제한(인증 5회/분 · 일반 60회/분), JWT 강화, 회원 탈퇴 시 데이터 파기, 반응형 대응 등.

**그 외**
- Resend 기반 비밀번호 재설정 이메일 인증 (데모/프로덕션 토글)
- Locust 부하 테스트 — 동시 접속 50명 조건에서 조회 API P95 18ms, 실패율 0%
- 한국어 에러 미들웨어 (Pydantic 422 응답을 한국어 메시지로 변환)
- 아키텍처 의사결정 기록(ADR) 4건 — 데이터베이스 · 프론트엔드 · 인증 · 브랜치 전략
- 문제 정의 · 화면 흐름 · R&R 문서화

## 판단과 근거

**데이터베이스 — [ADR-0001](docs/05-adr/ADR-0001-database.md)**

부트캠프가 제공한 MySQL + Tortoise 템플릿을 PostgreSQL 16으로 교체했습니다.
포인트 적립 내역이나 감정 기록처럼 형태가 바뀌는 메타데이터에 JSONB가 필요했는데 MySQL 8.0에는 JSON만 있어 기각했고,
혈압·혈당·eGFR 같은 의료 수치의 트랜잭션 무결성 때문에 MongoDB를, 다중 사용자 동시 쓰기 때문에 SQLite를 기각했습니다.

ORM은 SQLAlchemy가 동기 기본이라 async 설정 부담이 있어, 비동기 우선이고 aerich 마이그레이션이 통합된 Tortoise를 유지했습니다.
감수해야 할 단점(멘토의 PostgreSQL 경험 부족, Tortoise 커뮤니티 규모, JSONB 인덱싱 비용)도 ADR에 그대로 적었고,
운영 중 마이그레이션 16개를 무중단으로 적용했습니다.

**프론트엔드 — [ADR-0002](docs/05-adr/ADR-0002-frontend-framework.md)**

백엔드를 FastAPI로 분리한 이상 Next.js는 기능이 겹쳐 기각하고 Vite + React 19 + TypeScript + Tailwind v4로 갔습니다.
상태의 90%가 서버 상태라 Redux/Zustand는 과하다고 보고 TanStack Query 캐싱으로 처리했으며,
고령 사용자를 고려해 번들을 가볍게 잡았습니다.

**검진지 OCR — 표 형식 결과지의 오탐**

표 형식 검진지에서 총콜레스테롤 칸이 HDL(고밀도 콜레스테롤) 값을 가로채는 오탐이 반복됐습니다.
CLOVA OCR이 글자 조각마다 줄바꿈 신호를 보내는 경우가 많아, 한 행으로 묶여야 할 글자들이 흩어진 것이 원인이었습니다.

- 줄바꿈 신호 대신 글자 조각의 **좌표**로 같은 행을 다시 묶고 가로 순서대로 정렬했습니다
- "고밀도"·"저밀도"가 들어간 행은 총콜레스테롤로 매핑하지 않도록 막았습니다
- HDL은 두 줄짜리 셀이라 이웃 행 숫자까지 끌어오는 문제가 있어, 셀 경계를 기준으로 읽는 전용 규칙을 따로 두었습니다

## 배운 것 · 한계

가장 오래 막힌 것은 기술이 아니라 초반 기획이었습니다. 어떤 서비스와 기능을 넣을지 팀 브레인스토밍으로 풀어나갔지만
여기서 시간을 가장 많이 썼고, 이 경험이 이후 프로젝트에서 설계를 먼저 문서로 확정하는 방식으로 넘어간 계기가 됐습니다.

- 팀 외부 사람이 사용한 적이 없어 실사용자 검증은 없습니다.
- 위험 예측 모델은 팀원 담당 영역이며, 저는 모델 성능에 대해 주장하지 않습니다.
- 부트캠프 기간 중 운영하던 배포 서버는 현재 내려가 있습니다.

- **Backend** — Python, FastAPI, Tortoise ORM + aerich, PostgreSQL 16

- **기타** — NAVER CLOVA OCR, Resend(이메일), Locust(부하 테스트), Gemini(일러스트 생성)
